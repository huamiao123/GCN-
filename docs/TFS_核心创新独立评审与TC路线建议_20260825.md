## 1 · 核心创新点评价：距离 TC 还差多少

### 1.1 致命问题一：那条 planner 规则就是 DGL 自己的规则

**本工作的 planner**（`python/tfs_train/execution_plan.py:664`）：

```python
order = "aggregate" if d >= k else "transform"
```

**DGL `GraphConv.forward` 中长期存在的分支**：

```python
if self._in_feats > self._out_feats:        # K > D
    feat_src = th.matmul(feat_src, weight)  # transform-first
    graph.update_all(...)                   # 稀疏宽度 = D
else:
    graph.update_all(...)                   # 稀疏宽度 = K
    rst = th.matmul(rst, weight)
```

两者**逐字相同**。

更关键的一点：**DGL 的反向是 autograd 从这个前向分解自动导出的**，因此反向的稀疏宽度也已经是 `min(K, D)`：

| 情形 | DGL 前向分解 | autograd 得到的反向 | 反向稀疏宽度 |
|---|---|---|---|
| K > D | `Z = HW`, `O = SZ` | `dZ = SᵀG`, `dH = dZ·Wᵀ`, `dW = Hᵀ·dZ` | **D = min(K,D)** |
| K ≤ D | `P = SH`, `O = PW` | `dP = G·Wᵀ`, `dH = Sᵀ·dP`, `dW = Pᵀ·G` | **K = min(K,D)** |

**结论：DGL 从来没有把宽梯度送进稀疏聚合。**
总结文档 §2.1 所说的"避免在 `D >> K` 时把宽输出梯度送入稀疏聚合"，描述的是一件 DGL 已经在做的事。

这也解释了 8-21 边界文档与 8-25 源码核查之间的那个矛盾：核查发现"代码里跑的本来就是 Q-first、树里根本没有 Y-first 实现"——因为 **Q-first 是这个形状下的默认结构，不是本工作发明的**。

> **审稿人视角**：熟悉 DGL 的评审会在 5 分钟内指出这一点，"创新 A" 会被一句话打掉。

**同时必须承认的一个事实**：在当前四张图的全部 8 个层形状上，`d >= k` 规则与 DGL 的 `in_feats > out_feats` 规则**判定完全一致，零反例**。一条与既有系统判定完全一致的规则，在方法论上无法作为"新贡献"。

---

### 1.2 致命问题二：BF16 vs FP32 精度不对等，且 DGL 官方已有 BF16 CPU 路径

**现状口径**（`scripts/run_final_pre_numa_authority_matrix.sh`）：

```bash
export HYBRID_DTYPE=fp32        # DGL 臂：stock GraphConv，FP32
# TFS 臂：BF16 internal + FP32 accumulation/master
```

由第 2.0 节的 roofline，这套 workload 的主导项是稀疏 gather 的**字节数**，而字节数与元素精度成正比。**BF16 对 FP32 在主导项上直接就是 2×**，与任何算法或 kernel 设计无关。

更严重的是：DGL 官方 2024-08 博客 *GNN training acceleration with BFloat16 data type on CPU*（<https://www.dgl.ai/blog/2024/08/10/bfloat16.html>）正是在 SPR/AMX 机器上做的，对大 OGB 数据集自称相对 FP32 最高 **5.04×**。

> 也就是说：当前报告的 1.78–2.53×，**在数字上低于 DGL 官方自己的 BF16 路径所声称的加速**。

**能力其实已经具备**：

- `python/tfs_train/standard_dgl.py` 中 `DGLGCN.force_bf16_activations` 已实现；
- runner 支持 `HYBRID_DTYPE=bf16_mixed`（`tests/hybrid_aggregatewide_bf16grad_strongdgl_v3.py:867`）。

**只是 48-cell 没有跑这一臂。这一臂不补，论文没有送审条件。**

### 1.3 致命问题三：静态首层聚合是未披露的预计算（已在源码中确证）

不是"可能触发"，而是**被 gate 强制触发、不触发即判 cell 失败**：

`scripts/validate_authority_plan.py:19`

```python
def expected_variant(k: int, d: int, layer: int) -> str:
    if layer == 0 and k <= d:
        return "aggregate_static_v3"
```

`scripts/run_final_pre_numa_authority_matrix.sh` 中若 plan 不匹配 → `code=94` → cell 标记 failed。

对应 kernel：`c3_prepare_static_aggregate_v3`（`v6_wide_aggregate_probe.cpp:1840`），注释原文："The static T0 cache removes only the sparse pull"。

触发情况：

| 图 | L0 形状 | `k ≤ d`? | 第 0 层 SpMM |
|---|---|:--:|---|
| Products | 100 → 128 | 是 | **整层预计算，200 epoch 全省** |
| Arxiv | 128 → 128 | 是 | **整层预计算，200 epoch 全省** |
| IGB-19 | 1024 → 128 | 否 | 保留（仅缓存 BF16 的 Hs） |
| IGB-2983 | 1024 → 128 | 否 | 保留（仅缓存 BF16 的 Hs） |

**定量（Products）**：nnz = 1.237×10⁸，w = 100，BF16 → 每次聚合 `1.237e8 × 100 × 2B = 24.7 GB`；layer-0 不需要 dX，故前向 + 反向两趟合计 **省 49.4 GB / step**，× 200 epoch。

同时，头条数字取的是 `median(epoch 2..200)`（`manifest.json` 的 `steady_epoch_scope`），**缓存构建成本落在 epoch 1，被排除在稳态数字之外**。

**判断**：这在 transductive full-batch 下数学上合法（S·X 确为常量），但它是 SGC / 预计算传播的**已知技术**，且 DGL baseline 未被给予同等待遇。它极可能就是 Products / Arxiv 那 2.0–2.5× 的主体。**必须做 on/off ablation 并在正文披露。**

### 1.4 另外两条会被直接退稿的

**(a) 没有收敛 / 精度证据。**

一篇混合精度**训练**加速论文，两份总结文档中 accuracy 一字未提。正式论证使用的是"梯度相对误差 ≤ 3%"这一 gate（`HYBRID_GRAD_TOL=0.03`）。**3% 的单步梯度误差对 200 epoch 训练不构成任何收敛保证。**

（CSV 中其实每 epoch 都记录了 `test_accuracy`，数据是有的，只是没有被组织进论证。）

**(b) baseline 只有 stock DGL 一个。**

TC 至少会要求：DGL-BF16、PyG（torch_sparse）、IPEX；相关工作需覆盖 CPU 侧 GNN 训练系统类工作，例如 ARGO（多核处理器 GNN 训练自动调优运行时，<https://arxiv.org/html/2402.03671v2>）。

### 1.5 那么真正剩下什么

诚实结论：**剩下一个工程贡献。**

`c3_backward_aggregate_highd_amx_v1`（`v6_wide_aggregate_probe.cpp:3576`）中的融合 panel kernel 是真东西：G 的一次 panel 内扫描同时喂 dH 的 GEMM 与 dW 的 GEMM，`z.y / z.yt / z.hp` 全部 panel-local，中间量不落 DRAM。这是 "consumer count = 2" 的真实实现，DGL / PyTorch 的算子边界做不到。

**但这是算子融合，不是定理。** 它撑得起 ICPP（已经撑过了），撑不起 TC 的"新贡献"栏。

---

### 1.6 如果要救「创新 A」，唯一的办法

把它从**规则**改写成**代价模型 + 前反向解耦**。

DGL 的判据只有 `K vs D`，**没有 d̄，没有 cache 容量**。8-21 文档已推出的不等式 DGL 没有：

```
d̄ < 2(D+K)/(D−K)     (D > K)   ⟹   Y-first 更优
```

但要成为创新，必须找到 **DGL 判错、而本工作判对的真实形状**。

**在纯 GCN 中这样的形状不存在** —— 前向与反向的最优选择恒等（两者都要 `min(K,D)`）。这正是它现在撑不起主线的根本原因。

它存在的位置是**前向被结构锁死、反向仍有自由度的模型**：

- **GraphSAGE** 的 `concat(h_self, h_neigh)`：前向必须 aggregate-first（聚合宽度 K、变换宽度 2K→D），但反向 dH 走 Y-first 还是 Q-first 存在真实自由度，**而 DGL 被 autograd 锁死在一条路径上**；
- **GAT**：`D = heads × d_head`，attention 使前向无法 transform-first；
- 带 residual / JK 连接的层。

**这是 DGL 结构上做不到、而本工作能做到的唯一位置。**

**建议**：主线扩到 GCN + GraphSAGE + GAT，创新点重定义为「**前反向解耦的 dataflow 选择 + 含 d̄ 与 cache 容量的代价模型**」。这条**单独仍撑不起 TC**，但它是修补现有 §2.1 的唯一办法，成本最低，应作为配菜。

## 2 · 当前实现的问题与优化空间

### 2.0 先立 roofline —— 它决定后面每一条值不值得做

每层每步：

- **dense**：`6NKD` FLOP（forward 2NKD + backward 4NKD）
- **sparse**：`2·nnz·w` 次 element-add，`w = min(K,D)`；字节 `4·nnz·w`（BF16，fwd + bwd）

```
t_sparse / t_dense = (4·nnz·w / BW) / (6NKD / F) = (2·d̄·w·F) / (3·K·D·BW)
```

代入典型隐藏层 `K = D = w = 128`，`d̄ ≈ 24`，`F = 32 核 × 2 TFLOP/s = 6.4×10¹³`，`BW ≈ 250 GB/s`：

```
t_sparse / t_dense ≈ (2·24·128·6.4e13) / (3·128·128·2.5e11) ≈ 32
```

> **稀疏聚合比稠密贵约 32 倍。AMX 在隐藏层里几乎是免费的。**
>
> 论文当前把 AMX 摆在卖点位置，方向是偏的 —— AMX 只在 IGB-2983 那种 `D = 2983` 的输出层才真正重要（该层 `6NKD = 2.29 TFLOP`）。

**再往下拆一层：gather 不是带宽受限，而是 MLP（memory-level parallelism）受限。**

- **访存侧**：每条边读 `w = 128` BF16 = 256 B = 4 条随机 cache line。SPR 每核约 12 个 LFB，HBM-cache 延迟约 150 ns → Little's law：`12 × 64B / 150ns ≈ 5.1 GB/s/核` → 32 核 ≈ **164 GB/s**，远低于 HBM 峰值。
- **指令侧**：每条边 `8×(vmovdqu + vpmovzxwd + vpslld) + 8×vaddps`，瓶颈在 port5 的 8 个 shuffle uop ≈ **8 cycle/edge** → 2 GHz 下 4 ns/edge/核；25M 边 / 32 核 × 4 ns ≈ **3.1 ms**。

**指令侧比访存侧快 8–13 倍。**

> **判据（后面反复使用）：唯一有意义的杠杆是「减少 gather 的次数 / 字节数」或「提高 MLP」。**

---

### P1 — sparse gather 中一条 prefetch 都没有（性价比最高）

**位置**：`v6_wide_aggregate_probe.cpp:506 pull_panel_impl`

**证据**：整个 `csrc/` 目录 `grep -c '_mm_prefetch\|__builtin_prefetch'` = **0**

既然是 LFB / 延迟受限而非带宽受限，软件预取是教科书解法：处理第 `e` 条边时，对 `ci[e+P]` 对应的源行发 `_mm_prefetch(..., _MM_HINT_T0)`，`P` 取 4–8（覆盖约 150 ns 延迟约需 8 条边的距离）。

SpMV / SpMM 文献上这一项常见 **1.3–2×**。

**工作量 < 50 行，风险极低。建议第一个做。**

---

### P2 — high-D 反向的 pull 前后有约 2.6 GB 纯格式搬运

**调用链**：`c3_backward_aggregate_highd_amx_v1:3869` → `c3_pull_only_amx_v1:2087`

以 IGB-2983（N = 10⁶，K = 128）计：

| 步骤 | 流量 |
|---|---|
| `d_padded`（N×Kp FP32，512 MB）→ 新建 BF16 张量 `hs` | 读 512 + 写 256 MB |
| gather → `pulled`（BF16） | **6.4 GB（正事）** |
| `pulled` → 新建 FP32 张量 `out` | 读 256 + 写 512 MB |
| caller 中 `d_h.mul_(scale.view({n,1}))` | 读 512 + 写 512 MB |
| **额外开销合计** | **≈ 2.6 GB（正事的 40%）** |

**已经写好但没接上**：`c3_pull_only_bf16_amx_v1:2197`，注释明确写着是"避免 BF16 → FP32 → BF16 round trip"，但 high-D 路径没有调用它，因为 `dh_amx_4c2a2b` 输出的是 FP32。

**修法**：

1. 让 `dh_amx_4c2a2b` 的 epilogue 直接输出 BF16（`amx_gemm_4c_epilogue`（`backward_v2_kernels.cpp:222`）已有带 scale/bias 的 epilogue 模板可抄）；
2. 把 `scale` 折进该 epilogue，消掉 `mul_`；
3. 改调 `c3_pull_only_bf16_amx_v1`；
4. 顺带 `d_padded` 由 512 MB 降到 256 MB。

**预估 IGB-2983 反向 −5% ~ −15%，零算法风险。**

---

### P3 — VNNI packing 全部是标量循环

三处：

1. `pack_rhs_into`（`v6_wide_aggregate_probe.cpp:1216`）：`for k: for n:` 标量散写，每次 backward 对 `Wᵀ` 做一遍。
2. `pack_h_panel_direct`（`backward_v2_kernels.cpp:155`）：每 panel 每线程 `rows × kp` 次标量散写，外加一次整 buffer `std::fill`。
3. `v6_wide_aggregate_probe.cpp:3648` 的 W 转置：

```cpp
for (q < dp)
  for (p < k)
    ws.wt[q*kp + p] = to_bf16(wp[p*d + q]);
```

stride = `d × 4 = 11932 B`。**38 万次标量 load，每次命中一条新 cache line，约 24 MB 流量去搬运一个 1.5 MB 的矩阵**，且每次 backward 都做一遍。

**标准做法**：16×16 AVX-512 分块转置 + `unpacklo/hi_epi16` 交织，通常 **5–10×**。

---

### P4 — dW 的最终 K×D 散射转置是单线程标量

`v6_wide_aggregate_probe.cpp:3852`

```cpp
for (int a = 0; a < k; ++a)
  for (int b = 0; b < d; ++b)
    dwp[a*d + b] = dwt[b*kp + a];
```

stride = `kp × 4 = 512 B`，38 万次读、每次一条新 cache line，且**单线程**。分块 + 并行即可。

> 注意不要与已测过的 `TFS_HIGHD_PARALLEL_REDUCE ≈ 1.00×` 混淆 —— 那测的是 reduce，不是这个 scatter。

---

### P5 — barrier 走最慢一档，且 authority profile 把快档锁死

`PersistentWorkerPool::worker_loop`（`v6_wide_aggregate_probe.cpp:390`）默认路径：

```cpp
pthread_mutex_lock(&mu_);
++completed_;
if (completed_ == active_) pthread_cond_signal(&done_cv_);
pthread_mutex_unlock(&mu_);
```

**32 个线程在同一把锁上串行完成通知。**

而 `scripts/tfs_standard_env.sh` 的 authority profile：

```bash
export TFS_GLUE_E8_ATOMIC_DONE=0 TFS_GLUE_E8_SPIN=0
```

**已经实现好的 atomic-done 与 spin 路径，在正式 48-cell 中是关闭的。**

对 IGB-2983（step ≈ 1400 ms）影响可忽略；但对 **Arxiv（N = 169k，step 仅几十 ms）**，每步几十个 parallel region × 十余 µs 即数个百分点。

> **Arxiv L2 从 1T 的 1.978× 掉到 2T 的 1.837× 这个反常点，头号嫌疑就是它。** 至少要做一次 A/B。

---

### P6 — `fused_db` 的融合粒度选错了，因此该否决结论不完整

`v6_wide_aggregate_probe.cpp:3689`

```cpp
const bool fused_db = highd_adaptive_flag("TFS_HIGHD_FUSED_DB", d <= 512);
```

→ `D = 2983` 走 `db.copy_(grad.sum(0))`，**再来一遍 11.9 GB FP32 全读**。

探索文档中测出融合版 0.954× / 0.962× / 0.969×，据此否决。**但那是因为融合实现把 D 宽向量的 read-modify-write 放在了 row 循环内**（`:3743`，`dbp[q] += gr[q]`），RMW 次数 = N = 10⁶。

**第三条路尚未尝试**：在 **panel 层面**竖着规约 —— panel 内先把 `512 × D` 沿行方向用 AVX 规约成一个 D 向量，**每 panel 只做一次 D 宽 RMW**，RMW 次数从 N 降到 N/512 = 1954 次。

这才是正确的融合粒度，能真正省掉那 11.9 GB 而不引入寄存器 / 缓存压力。

> 当前结论"宽 D 下融合必然更慢"是被实现粒度带偏的，应重测。

### P7 — train ratio 0.6 撞上 active-row 阈值 0.25，最后一层白算 40%

- `tests/hybrid_aggregatewide_bf16grad_strongdgl_v3.py:95`：`n_train = int(N * 0.6)`
- `scripts/tfs_standard_env.sh`：`TFS_E13_ACTIVE_MAX_DENSITY=0.25`

→ **active-row 全程未启用。**

但最后一层的 O 只有 train 行进入 loss，而 `D = 2983` 时这是最贵的一层。数学上完全等价地只计算 train 行：`dense 0.6×`、`Q = GWᵀ 0.6×`、`dW = P[train]ᵀ·G[train] 0.6×`。

阈值 0.25 是为"稀疏到足以省下 gather"设定的，但 **dense / epilogue 的节省是线性的，任何 density < 1 都省**。这里应拆成两个独立阈值（gather 阈值 vs dense 阈值）。

### P8 — loss / eval 的 PyTorch 胶水是共同的 Amdahl 天花板，且从未测量（最重要）

`tests/hybrid_aggregatewide_bf16grad_strongdgl_v3.py:955`

```python
loss = F.cross_entropy(logits.float()[ds.train_mask], labels[ds.train_mask])
```

IGB-2983 每训练步的流量估算：

| 操作 | 流量 |
|---|---|
| `logits[train_mask]`（600k × 2983 advanced-index 拷贝） | 读 11.9 + 写 7.2 GB |
| cross_entropy forward（log_softmax） | 约 14.4 GB |
| cross_entropy backward | 约 14.4 GB |
| 反向 scatter 回 N×2983 零张量 | 约 19 GB |
| **合计** | **约 65+ GB** |

**这一部分 TFS 与 DGL 完全相同。** 实测 `evaluation_ms = 443 ms` 与该量级吻合。

> **推论：IGB-2983（1.78–2.22×）低于 IGB-19（2.17–2.30×）的头号原因，是这段共享胶水的 Amdahl 稀释，而不是"Y-first 失效"—— Q-first 本来就已经在跑。**
>
> 8-21 文档 §8.1 把那个 −27% 归因给 Y-first 失效，**该归因是错的**。

**必须先做的事：出一张 per-phase 时间分解表。**

代码里有 `TFS_HIGHD_NATIVE_PROFILE`，但 authority 运行时 `TFS_INTERNAL_PROFILE=0`。

> 没有这张表，后续所有优化都是盲猜 ——
>
> **8-25 当天四个候选优化全部落空（0.954× / 1.001× / 1.000× / 1.0003×），正是缺这张表的直接后果：在优化一个不知道占比多少的东西。**

## 3 · 可以做成硬核创新的方向

**判据来自 2.0 节：任何"大幅提升"的方案必须减少 gather 的次数或字节数。**

---

### 3.0 先排除的方向（这本身是可写进论文的负面结果）

> **图重排序（Gorder / Rabbit Order / RCM）与 source-locality 调度，在这台机器上数学上就没有空间。**

Xeon Max 9462 的 HBM 是 **cache mode**（已确证：8 个 NUMA node 均带 CPU，无 HBM-only node）。单 socket 约 32 GB memory-side cache。而 feature working set：

| 数据 | 大小 | 是否装得进 HBM cache |
|---|---|:--:|
| Products 特征（2.45M × 100 FP32） | 约 1.0 GB | 是 |
| IGB static Hs（1M × 1024 BF16） | 约 2.0 GB | 是 |
| IGB `d_padded`（1M × 128 FP32） | 约 0.5 GB | 是 |

**全部装得进。** 因此局部性优化的收益上限就是"HBM 命中 vs DDR 命中"这一档，而工作集已经全在 HBM 里了。

> **这就是 source-locality panel scheduler 精确跑出 1.000× 的原因 —— 不是实现不好，是这条路在这台机器上没有空间。**

**可以写进 TC 的一句话：**

> **HBM 抹平了全批 GNN 训练的 locality wall。在 memory-side HBM cache 系统上，只有"减少访问次数"的优化能存活，"减少访问距离"的优化不能。**

这句话能一次性解释探索文档中四个失败候选（fused db / parallel dW reduce / source scheduler / interleave）。

**注意**：同一条推理**不能**排除"减少边数"的优化 —— 即使工作集全在 HBM 内，边数减半时间仍然减半。这正好指向方向 1。

---

### 方向 1（最推荐）：精度约束下的聚合冗余消除

#### 数学基础

Aggregation 在 `(+, ·)` 半环上可结合、可交换。若目的节点 `i` 与 `i'` 共享邻居集 `C`，则 `Σ_{j∈C} h_j` 被重复计算。引入辅助节点 `a = Σ_{j∈C} h_j`，边数由 `|C|·2` 降为 `|C| + 2`。

这就是 HAG（*Redundancy-Free Computation Graphs for Graph Neural Networks*, Jia et al., MLSys 2020，<https://arxiv.org/pdf/1906.03707>），原文报告聚合次数最多降 **6.3×**、端到端训练吞吐最多 **2.8×**。

#### 为什么在本工作中是新的（HAG 是 prior art，差异必须写死）

**(1) HAG 是 GPU / FP32 的；BF16 下重构聚合 DAG 会改变求和顺序与舍入。**

辅助节点结果若以 FP32 回写则省不下带宽（省带宽正是目的）；若以 BF16 回写，则深度为 `h` 的 DAG 相对误差上界为

```
(1 + u)^h − 1,     u = 2^(−8)
```

这给出一条硬约束：

> **在 `‖ΔP‖ / ‖P‖ ≤ ε` 的前提下最大化边数削减** —— 一个带深度 / 误差预算的聚合 DAG 构造问题。

**这是定理形状的贡献，HAG 没有**，而且天然接上本工作已有的 "BF16 internal + FP32 accumulation/master" 契约。

**(2) 摊销 regime 不同。**

HAG 原文的挖掘开销在 mini-batch 场景下是痛点；而本工作是 full-batch transductive、图不变、200 epoch × 2 层 × 2（fwd/bwd）= **800 次聚合**，挖掘成本几乎完全被摊销。

> 这是让一个"旧"技术在新 regime 下合法重生的论证方式，也是正面回应"GNN 融合收益是幻觉"一类批评的方式。

**(3) 覆盖面比现有 static cache 大。**

它是 static Hs / static aggregate cache 同一哲学的自然延伸，但**能覆盖 static cache 覆盖不到的层**：IGB 的 1024→128 transform 层、所有隐藏层、以及**所有反向聚合**。

#### 收益估计

稀疏占层时间约 32/33 → 边数降 2× → 层加速约 **1.9×**；叠加当前 2× → 名义 3.5–4×。

#### 必须先做的实验（几小时，纯离线）

> **E-A：四张图的共同邻居冗余度统计。**
>
> 对每张图统计 `(dst 对, 共同邻居数)` 分布，估计可省边比例与所需辅助节点数。
>
> Products 是 Amazon 共购图、聚簇强，预期冗余高；Arxiv 引用图预期低。
>
> **纯 Python / C++ 脚本，不写 kernel，直接决定这条路值不值得走。**

#### 风险

- 辅助节点带来两阶段依赖，实现比平坦 CSR gather 复杂；
- 必须证明 BF16 下精度不掉 —— 但这正好与"补收敛证据"这项工作合并完成。

---

### 方向 2（最"新"）：反向专用的结构化无偏边采样

#### 动机

前向必须精确（决定 loss 与模型输出），但**梯度只需要是无偏估计** —— SGD 本来就在噪声中工作。

现有采样方法（GraphSAGE / FastGCN / LADIES / GraphSAINT）都是为了**降内存 / 降规模**而在**前向**采样，代价是前向也变成近似。

**本方向做相反的事：前向精确，只在反向的 `dH = SᵀQ` 上采样。**

#### 数学基础

```
dH_i = Σ_{j∈N(i)} s_i · s_j · q_j
```

以概率 `p_e` 采样边 `e`、用 `1/p_e` 加权 → 无偏。方差：

```
Var = Σ_e (1/p_e − 1) · ‖s_i · s_j · q_j‖²
```

在 `Σ_e p_e = m` 约束下最小化 → 最优 `p_e ∝ ‖s_i · s_j · q_j‖`（重要性采样）。

#### 关键：把采样率与硬件预算而非超参连起来

设 dropout(p=0.5) 已经引入的梯度方差为 `σ²_drop`，选 `m` 使 `σ²_sample ≤ α·σ²_drop`（`α ≤ 1`）。

> **低于已有噪声地板的方差是免费的。**
>
> 这是可证、可测的判据，而不是调一个超参。

#### 系统侧的真正贡献（这才是让它成为 TC 而非 ICLR 论文的部分）

随机逐边采样会**摧毁**本来就很差的局部性 —— 采 50% 的边不会省 50% 的时间，因为被跳过的边与被保留的边共用 cache line。

因此必须**结构化采样**：以 `(dst panel × src block)` 或每行 CSR 的连续段为采样单元，使被跳过的边真的对应被跳过的 cache line。

> **"无偏"与"访存友好"这两个约束的联合求解，就是 co-design 的定理。**

#### 收益估计

反向稀疏那一趟 2–4×；反向稀疏约占整层的一半 → 层加速 1.5–1.8×。

#### 必须做的实验

- **E-B1**：测 `‖q_j‖` 的分布（是否重尾 → 重要性采样是否有效）
- **E-B2**：测 dropout 的梯度方差，作为噪声地板
- **E-B3**：端到端 200 epoch 精度曲线 —— **这条正好补上当前缺失的收敛证据**

#### 审稿反驳预案

> "这不就是 DropEdge？"

差异必须写死：

- DropEdge 改**前向**、是**正则化**、**有偏**；
- 本方法**前向精确**、**无偏**、采样率由**方差预算导出**。

相关工作必须引并说明区别：

- LMC: Fast Training of GNNs via Subgraph Sampling with Provable Convergence（ICLR'23）— <https://arxiv.org/pdf/2302.00924>
- Provably Convergent Subgraph-wise Sampling for Fast GNN Training — <https://arxiv.org/pdf/2303.11081>

（它们是 subgraph-wise mini-batch，本方法是 full-batch backward-only。）

---

### 方向 3：dataflow 规则升级为代价模型 + 前反向解耦

即 1.6 节所述。

- **单独撑不起 TC**，但它是修补现有第一创新点的唯一办法，成本最低；
- 第一步必须是**构造出 DGL 判错的形状** —— 在纯 GCN 中不存在，因此必须把模型扩到 GraphSAGE / GAT；
- 建议定位为配菜，不是主菜。

---

### 方向 4：把稀疏聚合本身喂给 AMX（密集块提取 + tile 复用）

#### 数学基础

一个 `16(dst) × 32(src)` 的邻接密集块，把 32 个源行一次装入一个 AMX tile，被 16 个目的行复用 → 源数据流量相对逐边 gather 降为

```
32·w / (512·ρ·w) = 1 / (16ρ)
```

其中 `ρ` 为块密度。**`ρ ≥ 1/16 = 6.25%` 才划算。**

吞吐上限很诱人：AMX 512 MAC/cycle vs AVX gather 约 32 add/cycle，**16×**。

#### 可行性

幂律图上随机块达不到该密度，但**按度排序把 hub 聚到一起**后可能可以（Products 前 1% 高度节点覆盖大量边）。

先例：ASpT（PPoPP'19）、SCV-GNN（<https://par.nsf.gov/biblio/10428794-scv-gnn-sparse-compressed-vector-based-graph-neural-network-aggregation>）。

#### 必须先做的实验（同样纯离线，几小时）

> **E-C：对四张图做「重排后 16×32 块的密度直方图 + 达到 ρ ≥ 6.25% 的块所覆盖的边比例」。**
>
> **若覆盖率 < 20%，直接放弃这条路。**

#### 风险

最高。收益上限也最高。属于"先算清楚再动手"的典型。
