# 2. 当前真实执行链

## 2.1 Authority 隐藏层

当前 `HybridGCN.forward()`：

```python
for conv in self.convs[:-1]:
    x = F.dropout(
        F.relu(conv(x, graph)),
        p=self.dropout,
        training=self.training
    )
return self.convs[-1](x, graph)
```

GCN native conv 的输出是 **FP32**。

下一层进入 native sparse/dense kernel 时，通常又调用：

```cpp
build_hs_bf16_exact(x, scale, ...)
```

其中核心逻辑为：

```cpp
Hs[i,k] = BF16_RNE(x[i,k] * scale[i])
```

因此动态隐藏层边界当前是：

```text
上一层 native conv
    ↓
FP32 H[N,K]
    ↓
PyTorch ReLU
    ↓
FP32 H_relu[N,K]
    ↓
PyTorch Dropout
    ↓
FP32 H_drop[N,K]
    ↓
下一层 build_hs_bf16_exact
    ↓
BF16 Hs[N,K]
```

这条链后面会详细讨论，它是当前多层模型最明显的全图内存流量问题之一。

---

## 2.2 Supervision-scoped terminal

当前 bounded terminal 的真实结构大致为：

```text
hidden FP32 [N,K]
    ↓
c3_prepare_static_hs_v1
    ↓
Hs BF16 [N,K]
    ↓
c3_selected_pull_bf16_shadow_v1
    ↓
P BF16 [M,K]
    ↓
for each row panel:
    P_panel
      ↓
    native AMX logits 或 torch.matmul
      ↓
    FP32 logits [R,D]
      ↓
    in-place log_softmax / exp / CE gradient
      ↓
    BF16 Gs [R,D]
      ├── native AMX dW
      └── torch.matmul(Gs, W^T) → Q [R,K]
    ↓
保存完整 Q[M,K]

autograd backward:
Q[M,K]
    ↓
rectangular sparse pull
    ↓
dH[N,K]
```

这已经比原始 full `N×D` terminal 好很多，但还没有真正做到“全链条流式化”。

# 3. S0-1：Wide-K 静态首层存在一个很大的数据流缺口

这是本次重新看 planner 后最值得重视的新结论之一。

## 3.1 当前 planner 的约束

`execution_plan.py` 仍采用：

```python
order = "aggregate" if d >= k else "transform"
```

而静态 T0 / aggregate cache 只有：

```python
static_v3_supported = (k <= 128 and d <= 128)
```

且还要求：

```python
order == "aggregate"
not compute_dx
```

Native producer 里也直接限制：

```cpp
TORCH_CHECK(k >= 1 && k <= 128)
```

因此像：

```text
IGB first layer:
K = 1024
D = 128
```

由于：

```text
D < K
```

会被自然归到 Transform-first：

```text
X W
 ↓
S(...)
```

这使它无法使用现有 static `S X` cache。

---

## 3.2 但从训练语义看，这个首层其实非常特殊

首层具有：

```text
X        固定
S        固定
train graph 固定
x.requires_grad = False
W        每 epoch 变化
```

所以：

\[
P_0 = S X
\]

完全可以只计算一次。

之后每个 epoch：

\[
Z_0 = P_0 W_0
\]

即可。

也就是说，本来每个 epoch：

```text
Transform-first:
X W
 ↓
S(XW)
```

可以重写成：

```text
cold start:
P0 = S X     ← 一次

steady state:
P0 W         ← 每 epoch
```

这不是近似，也不需要采样；唯一需要严格验证的是你们 BF16 rounding 位置改变以后和当前 authority 的数值合同是否满足现有 tolerance。

---

## 3.3 为什么这个可能比普通 kernel 优化大得多

如果首层是：

```text
N = 1M
K = 1024
D = 128
```

Transform-first 每 epoch 都需要：

1. `X[N,1024] × W[1024,128]`
2. 对 `N×128` 做一次 sparse aggregation。

Static aggregate cache 后则：

1. 冷启动一次 `S X`；
2. 每 epoch 只做 `P0[N,1024] × W[1024,128]`。

虽然 dense GEMM 仍在，但 **每 epoch 的首层 sparse graph traversal 被完全删除**。

对 sparse aggregation 本身占比较高的真实图，这可能比继续优化某一个 sparse kernel 10% 更有价值。

---

## 3.4 推荐实现

新增一个与原 `static_v3` 分开的路径：

```text
aggregate_static_widek_v1
```

条件：

```text
layer == 0
input_static
graph_static
feature_static
compute_dx == False
K > 128 allowed
memory_budget permits N*K BF16 cache
```

不要再要求：

```text
D >= K
```

即首层 static semantics 可以覆盖普通 dimension-only order rule。

### Planner 应改成

```text
if static first layer and no dX:
    compare:
        static-SX cache
        ordinary transform-first
else:
    ordinary D/K association
```

### 验收

必须单独测：

- cold build time；
- steady first-layer forward；
- full train step；
- cache bytes；
- loss/grad drift；
- amortization epochs；
- 不同 K：128/256/512/1024/2048；
- 不同 N / E。

### 结论

**优先级：S0。**

这是一个真正改变“首层每轮是否还需要碰图”的数据流优化。

# 4. S0-2：隐藏层 FP32 Glue 仍产生巨大全图流量

## 4.1 当前问题

Authority hidden layer：

```text
conv output FP32
→ ReLU
→ Dropout
→ 下一层 scale
→ FP32→BF16
```

至少有多个完整 `N×K` tensor pass。

以 `ogbn-products`：

```text
N = 2,449,029
K = 128
```

一个 FP32 hidden：

\[
N\times K\times4 \approx 1.254\ GB
\]

一个 BF16 hidden：

\[
N\times K\times2 \approx 0.627\ GB
\]

仅按最简单的读写估算：

```text
ReLU:
FP32 read + FP32 write        ≈ 2.508 GB

Dropout:
FP32 read + FP32 write        ≈ 2.508 GB

next Hs conversion:
FP32 read + BF16 write        ≈ 1.881 GB
```

合计约：

\[
6.90\ GB
\]

**每一个隐藏层边界**。

这还没有算：

- Dropout mask；
- allocator / cache eviction；
- 上一层最终 FP32 输出写回；
- 下一层后续 sparse feature read。

---

## 4.2 为什么这是 L3/L4 后最重要的问题

Terminal optimization 只优化最后一层。

层数增加后：

```text
L2:
hidden → terminal

L3:
hidden → hidden → terminal

L4:
hidden → hidden → hidden → terminal
```

每增加一个隐藏层，就多一整套：

```text
FP32 activation
ReLU
Dropout
BF16 conversion
full-graph sparse
```

因此 Products L3 的 terminal speedup 被 Amdahl 稀释，不只是“terminal 占比变小”，还意味着系统中存在大量未优化的 inter-layer traffic。

---

## 4.3 推荐：Fused Inter-Layer Activation Producer

目标不是单纯做 inplace ReLU，而是把：

```text
ReLU
+
Dropout
+
source scale
+
FP32→BF16
```

尽量合并成一个流式 producer。

当前：

```text
FP32 H
→ FP32 ReLU H
→ FP32 dropout H
→ BF16 scaled Hs
```

目标：

```text
FP32 conv output
       ↓ one pass
ReLU + dropout-mask + scale + BF16-RNE
       ↓
BF16 Hs consumed by next TFS layer
```

如果 backward 需要激活信息：

- ReLU 只需保存 bit mask / 可重构 mask；
- Dropout 保存 RNG seed / bitpacked mask；
- 不需要为了 backward 保留多个 FP32 materialized activation。

更激进的版本：

```text
上一层 AMX epilogue
→ 直接做 ReLU / dropout / 下一层需要的 BF16 staging
```

但这会跨 layer/fusion 边界，工程复杂度更高。

---

## 4.4 数值合同

必须保持：

```text
ReLU
→ Dropout
→ source scale
→ BF16 round-to-nearest-even
```

的语义顺序。

不能为了融合偷偷变成：

```text
scale
→ BF16
→ ReLU
```

否则数值路径改变更大。

---

## 4.5 潜力

这是**全图、每隐藏层重复发生**的流量。

因此：

- L2：中等；
- L3/L4/L8：越来越重要；
- memory-bandwidth-bound graph：潜力更大。

不能在没有 profile 前声称固定 1.3x，但这是目前最值得做的**深层模型系统优化之一**。

**优先级：S0。**

# 5. S0-3：Terminal 仍没有真正做到“宽张量即产即用”

这是当前 supervision terminal 最明显的大口子。

---

## 5.1 已经解决了什么

当前已经避免：

```text
full N×D logits
full M×D persistent logits
full M×D persistent gradient
global P^T materialization（native dW path）
```

并已有：

```text
native compact logits
native compact dW
in-place log-softmax
fused db
T4 tail
```

这些不应该重复做。

---

## 5.2 但当前仍然物化一个很大的 Gs panel

每个 bounded row panel：

```python
logits: FP32 [R,D]

...

gs = c3_scale_grad_bf16_db_v2(
    logits, panel_scale, threads
)
```

得到：

```text
Gs BF16 [R,D]
```

然后：

```text
consumer 1:
native dW reads Gs

consumer 2:
torch.matmul(gs, weight_t) reads Gs again
```

如果：

```text
R = 300,000
D = 2,983
```

则：

### FP32 logits panel

\[
300000\times2983\times4 \approx 3.58\ GB
\]

### BF16 Gs panel

\[
300000\times2983\times2 \approx 1.79\ GB
\]

仅 Gs：

```text
write Gs once       1.79 GB
read for dW         1.79 GB
read for Q          1.79 GB
```

约：

\[
5.37\ GB
\]

一个 300k-row panel。

600k supervised rows有两个大 panel，单单 Gs 的“写一次 + 两次读”就约：

\[
10.7\ GB
\]

还没有算 logits 的 log-softmax / exp / target / gradient pass。

所以 bounded CE **解决了峰值内存**，但并没有完全解决**宽 tensor 的 DRAM scan volume**。

---

# 6. S0-3a：Q = Gs W^T 仍是 PyTorch matmul

当前代码：

```python
q[r0:r1].copy_(
    torch.matmul(gs, weight_t)
)
```

而同一条 terminal 链中：

```text
P W      → 已有 native AMX logits
P^T Gs   → 已有 native AMX dW
Gs W^T   → 仍然 PyTorch
```

三者都是大 dense GEMM。

对：

```text
M=600k, D=2983, K=128
```

`Q = Gs W^T` 与 classifier `P W` 在主 FLOP 量级上接近。

这意味着当前还剩下一个非常明显的“第三块大 GEMM”。

---

## 6.1 推荐第一步：Native Compact Q

新增类似：

```text
c3_compact_q_bf16_amx_v1
```

输入：

```text
Gs [R,D] BF16
W  [K,D] FP32/BF16 packed
```

输出：

```text
Q [R,K] BF16 或 FP32→BF16 direct epilogue
```

目标：

- AMX BF16 accumulate FP32；
- 直接 RNE 写 BF16 Q；
- 不先生成 FP32 Q 再 `.to(BF16)`；
- 使用与 dW 相同的 row ownership；
- 重用 forward 已准备的 `W^T` / packed W。

---

## 6.2 更好的最终形态：dW + Q 联合消费 Gs

不是说“一条 AMX 指令同时算两个 GEMM”，而是把：

```text
Gs producer
```

和：

```text
dW consumer
Q consumer
```

放进同一个 native pipeline。

当前：

```text
Gs huge panel
 ↓ write memory
dW reads entire Gs
Q  reads entire Gs again
```

目标：

```text
small Gs microblock
      ├── immediately update dW
      └── immediately produce Q
then discard
```

让 Gs 更像一个**短生命周期 tile**，而不是一个 GB 级 tensor。

---

# 7. S0-3b：建议直接做 Whole-Terminal Native Micro-Engine

这是当前 terminal 方向最值得做的最终版本。

## 7.1 当前 bounded panel 太“大”

`supervision_dense_plan.py` 当前：

```python
row_tile = min(selected_rows, 300_000)
```

这个 row tile 是为了限制峰值内存，但：

```text
300,000 × 2,983 FP32
```

仍然是 3.58GB。

这根本不可能作为 cache-resident working set。

所以现在的 `row_tile` 更准确地说是：

> **memory-bounded macro panel**

而不是：

> cache-local micro panel。

---

## 7.2 推荐两级 panel

```text
M supervised rows
    ↓
macro panel
例如 32k/64k/128k
    ↓
micro panel
例如 256/512/1024 rows
    ↓
AMX / CE / Gs / dW / Q
```

### Micro panel 内执行

```text
P_micro
  ↓
AMX classifier
  ↓
FP32 logits scratch
  ↓
exact row max / exp / sum / target
  ↓
BF16 Gs microblock
  ├── AMX dW partial
  └── AMX Q
  ↓
discard logits/Gs
```

最终持久量只剩：

```text
Q[M,K]
dW[K,D]
db[D]
loss
```

---

## 7.3 必须一起解决 W packing

当前 native compact logits C++ 注释已经明确写着：

> weight packing is deliberately included in the call until a whole-terminal fused interface can safely reuse it.

其实现每次调用仍：

```text
logical W
→ padded W
→ packed W
→ AMX
```

现在 row panel 只有 2 个时还能接受。

如果以后 micro panel 变成 512 rows，而每个 micro panel 都重新 pack W，性能会直接崩掉。

因此 Whole-Terminal API 必须：

```text
terminal call begin
    ↓
W → BF16 / W^T / AMX pack once
    ↓
for all micro panels:
    reuse packed W / W^T
```

---

## 7.4 为什么这个方向可能继续显著提高当前 2.0965x

当前 2.0965x 后，已经消掉了大量原 full terminal work。

下一层主要残留：

- wide FP32 logits pass；
- BF16 Gs 大量写读；
- Q torch matmul；
- W packing / framework boundary；
- full P materialization。

Whole-Terminal Micro-Engine 正好一次性攻击这些剩余项。

**优先级：S0。**

# 8. S0-4：D-slab 解决了 workspace，但引入了结构性重复工作

这个问题要分 Aggregate 和 Transform 两条路说。

---

# 9. Aggregate High-D D-slab 的真实执行

核心数学：

\[
dW = P^T G_s
\]

\[
dP = G_s W^T
\]

\[
dX = S^T dP
\]

沿 D 分 slab：

\[
G_s = [G_0,G_1,\dots,G_{S-1}]
\]

\[
W = [W_0,W_1,\dots,W_{S-1}]
\]

于是：

\[
dW_s = P^T G_s
\]

不同 slab 对应 `dW` 的不同列。

但：

\[
dP = \sum_s G_s W_s^T
\]

---

## 9.1 当前 native d-slab adapter

当前 Python 逻辑：

```python
for d0, d1 in ranges:
    part_dx, part_dw, part_db, _ = native(
        grad[:, d0:d1].contiguous(),
        pulled,
        weight[:, d0:d1].contiguous(),
        rowptr,
        colidx,
        scale,
        threads,
        compute_dx
    )

    if compute_dx:
        dx.add_(part_dx)

    dw[:, d0:d1].copy_(part_dw)
```

这带来四个问题。

---

## 9.2 问题 A：每个 slab 都可能完整 sparse scan

每次 native 调用内部都完成本 slab 的：

```text
Gs_s
→ dP_s
→ sparse A^T dP_s
→ part_dx_s
```

如果：

```text
S = 12 slabs
```

就可能：

```text
CSR scan × 12
```

Planner 自己也把：

```text
aggregate_highd_dslab:
sparse_scans = slab_count
```

记录为结构成本。

---

## 9.3 问题 B：`dx.add_(part_dx)` 重复扫描完整 N×K

每个 slab 返回：

\[
part\_dx_s\in R^{N\times K}
\]

然后：

\[
dx \mathrel{+}= part\_dx_s
\]

所以每个 slab 都要：

```text
read dx[N,K]
read part_dx[N,K]
write dx[N,K]
```

对于大 N/K，这是非常重的额外内存流量。

---

## 9.4 问题 C：列切片 `.contiguous()` 复制整个逻辑 G

```python
grad[:, d0:d1].contiguous()
```

对于 row-major `[N,D]` 来说，列 slab 通常不是 contiguous。

所以每个 slab 都：

```text
read source G slice
→ copy to contiguous slab
→ native 再读一次
```

所有 slab 合起来，基本相当于额外完整搬运一遍 `N×D` G。

`weight[:, slab].contiguous()` 也有同类问题，只是 W 远小于 G。

---

## 9.5 问题 D：D-slab 是“内存安全实现”，不是理想性能实现

现有 D-slab 的主要作用是控制：

\[
threads\times K_p\times D_p\times4
\]

的 thread-local dW workspace。

这一步是合理的。

但现在用：

```text
重复 sparse
+
重复 dx
+
slab copy
```

换来了 workspace bounded。

因此当前 D-slab 仍有非常清楚的下一阶段优化空间。

---

# 10. 推荐：True Native Single-Scan D-slab Backward

目标：

```text
for each N row panel:
    dP_panel = 0

    for each D slab:
        consume G slab
        update dW slab
        dP_panel += Gs_s @ W_s^T

    dP_panel FP32
        ↓ RNE once
    dP_bf16 panel

所有 row panel完成
        ↓
one sparse A^T dP
        ↓
dX
```

核心：

\[
dP = \sum_s G_s W_s^T
\]

必须先在 dense 域完成 D reduction，再做：

\[
A^T dP
\]

一次。

### 相比当前

```text
当前:
D slab × S
  → dense
  → sparse
  → full dx
  → add

目标:
D slab × S
  → dense accumulate dP

最后:
sparse × 1
```

---

## 10.1 现有代码已经有 reference 候选，但还没成为高性能 production kernel

Planner 中已有：

```text
aggregate_highd_single_scan
```

但当前：

```text
performance_state = experimental
validated_for_auto = False
```

`final_pre_numa` 环境也明确：

```bash
TFS_AGGREGATE_DSLAB_SINGLE_SCAN=off
```

所以正确的下一步不是“重新发明 single-scan”，而是：

> 把 reference 语义做成真正 AMX-native、row-panel-aware、workspace-bounded 的生产内核。

---

## 10.2 注意适用范围

典型：

```text
K=128, D=2983, 32T
```

full-D local dW workspace往往仍能放进当前预算，因此可能直接走：

```text
aggregate_highd_full
```

而不是 D-slab。

所以这个优化不能用来解释 IGB-2983 当前 2.0965x cell 的下一步收益。

它主要针对：

```text
K×D 更大
threads 更多
full-D private dW 放不下
```

的 shape。

**优先级：S0，但 shape-specific。**

# 11. Transform-High-D D-slab 还有更明显的重复 CSR 问题

Transform-first backward：

\[
dT = S^T G_s
\]

\[
dW = H^T dT
\]

\[
dH = dT W^T
\]

如果 D 被切成 S slab：

```text
G0 → S^T G0
G1 → S^T G1
...
```

天然就是：

```text
CSR scan × S
```

当前 wrapper 同样有：

```python
grad.narrow(1, d0, d1-d0).contiguous()
weight.narrow(...).contiguous()
```

以及：

```python
dx.add_(part_dx)
```

的问题。

同时 native 返回的 `_part_db` 在部分 wrapper 中被丢弃，外层又：

```python
db = grad_output.sum(0)
```

形成额外整块 grad scan。

更重要的是，当前 `final_pre_numa`：

```bash
TFS_TRANSFORM_HIGHD_NATIVE=off
TFS_TRANSFORM_HIGHD_SINGLE_SCAN=off
```

因此这一块更多还是“待晋级研究路径”，不能写成当前 authority 已经稳定使用。

# 12. Transform-High-D forward 也按 D slab 重复 sparse traversal

C++ 当前 wide transform forward：

```cpp
for (start = 0; start < d; start += transform_d_tile) {
    wt = W[:, start:start+td].contiguous();
    transformed = matmul(Hs, wt);

    // sparse pull for this D slab
}
```

源码注释已经明确：

> one logical CSR traversal per macro D slab.

也就是说：

```text
D=1024
d_tile=256
→ 4 次图遍历
```

如果：

```text
K>D
```

所以 planner 选择 Transform-first，但 D 本身仍很大，这个 repeated sparse scan 可能迅速把理论 FLOP 优势吃掉。

## 12.1 这里可能需要的不只是调 D_tile

应该让 planner 真正比较：

```text
Transform:
dense H×W
+
ceil(D/d_slab) × sparse_scan_cost(D_slab)

vs

Aggregate:
one sparse scan at K width
+
dense P×W
```

当前：

```text
D < K → transform
```

只是数学维度启发式，无法表达：

```text
D 仍然很宽
图非常大
CSR scan 很贵
```

的情况。

这属于后续真正的 cost-model 空间。

# 13. P1-1：确认存在的 BF16 → FP32 → BF16 无效往返

这是之前“精度转换冗余”里最具体、最容易直接修的一处。

当前 `aggregate_saved_v4` backward 存在：

```cpp
Gs = BF16
Wb = BF16

dp = matmul(Gs, Wb^T)
     .to(FP32)

dh = c3_pull_only_amx_v1(dp, ...)
```

但 `c3_pull_only_amx_v1()` 接收 FP32 后，内部会：

```text
FP32 dP
→ BF16 dP
→ sparse accumulate
→ FP32 output
```

也就是说这条链实际上是：

```text
BF16 GEMM output
    ↓
FP32 dP materialization
    ↓
BF16 conversion
    ↓
sparse pull
```

而代码中已经存在：

```text
c3_pull_only_bf16_amx_v1
```

它就是专门为了避免：

```text
BF16 → FP32 → BF16
```

往返。

---

## 13.1 最直接的修改

当前：

```text
dp = BF16 matmul
→ to(FP32)
→ c3_pull_only_amx_v1
```

改为：

```text
dp_bf16 = BF16 matmul
→ c3_pull_only_bf16_amx_v1
```

直接删掉完整 `N×K` FP32 dP 中间量和一次 conversion。

---

## 13.2 进一步版本

更理想：

```text
Gs × W^T
AMX FP32 accumulator
    ↓
直接 RNE 写 BF16 dP
    ↓
BF16 sparse pull
```

这样：

- 不产生 FP32 global dP；
- 不经历 framework BF16 output / float cast；
- 可与 High-D native kernel 统一。

**优先级：P1，易做、低风险。**

---

# 14. P1-2：Supervision terminal 仍先转换整个 Hs[N,K]

当前：

```python
hs = c3_prepare_static_hs_v1(
    hidden, scale, threads
)
```

即使 terminal 只需要：

```text
M supervised destinations
```

仍先对所有：

\[
N
\]

个 source rows 做：

```text
FP32 hidden
→ scale
→ BF16 Hs
```

之后 selected pull 才只访问 selected rows 对应的 source。

---

## 14.1 这里首先应该统计 U/N

定义：

\[
U_M =
\text{selected destination rows 实际触及的 unique source nodes}
\]

统计：

\[
|U_M| / N
\]

### 如果

```text
U/N ≈ 0.9~1.0
```

则 source compaction 基本没意义。

### 如果

```text
U/N ≈ 0.3~0.6
```

则完整 `N×K` Hs conversion 明显有浪费。

---

## 14.2 可选方案

### A. Compact source Hs

一次性构造：

```text
global_source_id → compact_source_id
```

terminal 每步只生成：

```text
Hs[U,K]
```

selected CSR 的 colidx 直接指向 compact source id。

### B. Fuse conversion into selected sparse pull

不先生成全量 Hs：

```text
selected pull
    ↓
load hidden[src] FP32
× scale[src]
    ↓
直接参与 FP32 accumulation
```

这个会改变 BF16 rounding 位置；如果要保持当前数值合同，必须：

```text
load FP32
× scale
→ RNE BF16 value
→ expand FP32 accumulation
```

可以在寄存器里做，不必 global write Hs。

---

## 14.3 风险

同一个 source 可能被多个 selected dst 反复用，如果每条 edge 都重新做 FP32→BF16 conversion，反而可能更慢。

因此必须根据：

```text
U/N
source reuse
K
E_M
```

决定：

```text
compact Hs
vs
on-the-fly
vs
full Hs
```

**优先级：P1，先测 U/N 再决定。**

# 15. P1-3：Terminal 仍完整物化 P[M,K]

当前：


先生成：

\[

\]

然后：

```python
for r0 in row panels:
    pp = pulled[r0:r1]
```

意味着：

```text

→ write whole P[M,K]
```

对于：

```text

BF16
```

P 约：

\[

相比 `M×D` 不算巨大，但仍是明确的全局中间量。

## 15.1 推荐：Selected Pull → Terminal Producer-Consumer Streaming

这个方向和 Whole-Terminal Native Micro-Engine 应一起做，而不是独立搞一个小 patch。

**优先级：P1/A。**

# 16. P1-4：authority_active fallback 仍构造完整 G[N,D]

在 compact terminal 的 mature active-row 回退路径里：

```python
grad_full = torch.zeros(
    (N, D)
```

```text
FP32
```

\[

\]

这不是小量。

## 16.1 推荐：Compact-Active Native Backward

不要：

```text

→ expand full G
→ mature active kernel
```

而是让 mature kernel 接收：

```text

```

active row scheduler / sparse backward 直接围绕 row_ids 工作。

目标：

> 保留 mature active-row 在高线程的 load balance / native 优势，同时保留 compact representation。

这可能让 Products 低 D / 高线程区域也真正获得 supervision scope 的收益。

**优先级：P1。**

# 17. P1-5：Selected / Rectangular shadow CSR 仍主要是 int64

Authority 原始 CSR 已经有：

```text

```

但 supervision shadow：

```text
selected row ids
transpose_colidx
```

仍主要使用 int64。

Products 文档里 selected adjacency entries 约：

```text

```

如果 colidx：

```text
int64 → ~271 MB
int32 → ~136 MB
```

单一 compact transpose edge stream 就能少约 135MB footprint。

更重要的是 sparse pull 是 bandwidth-bound，索引宽度直接影响 edge-side memory traffic。

## 17.1 推荐

给 shadow operator 增加：

```text

transpose_colidx int32
```

并把合法性在 scope build 时一次性验证。

不要在每 epoch 验证。

**优先级：P1/P2；收益不会像 terminal fusion 那么大，但性价比高。**

# 18. P1-6：Selected forward 仍在原 full CSR 上跳段

`SupervisionScope.build()` 已经构造了：

```text
selected transpose CSR
```

用于 backward。

但 forward selected pull 仍基于：

```text
row_ids + original full rowptr/colidx
```

去访问 selected rows 对应的 CSR segment。

如果 selected rows 很稀疏，例如 Products 约 8% supervised rows，那么 edge ranges 在原 CSR 中是分散的。

---

## 18.1 可构造 compact selected-forward CSR

冷启动一次生成：

```text
selected_rowptr [M+1]
selected_colidx [E_M]
```

这样 forward：

```text
for local row 0...M
    scan contiguous selected edges
```

优点：

- selected edge stream 更连续；
- 更容易使用 int32；
- selected pull 不再需要 `row_ids→global rowptr` 两级索引；
- 更适合后续 producer-consumer streaming；
- 更容易做精确 edge-balanced scheduling。

这并不是“共享邻居重排”，只是把已经决定保留的 selected rows compact 化。

**优先级：P1。**

# 19. P2：Weight BF16/pack 在 forward/backward 之间仍有重复

普通 forward 中多处：

```cpp

```

High-D backward 又：

```text

→ Wt BF16
→ pack
```

compact logits 当前也明确每次调用：

```text

→ pad
→ packed_w
```

训练中：

```text

```

因此一个 train step 内：

```text

```

与：

```text

```

可以共享同一版本。

## 19.1 推荐 Versioned Weight Staging

按：

```text
_version
shape
```

缓存：


optimizer 更新后 `_version` 变化，再重建一次。

## 19.2 优先级

W 通常远小于 `N×K` / edge feature traffic，所以这不是第一优先级。

但 Whole-Terminal Micro-Engine 必须做，因为微 panel 不能每次 pack W。

**优先级：P2；作为 fused terminal 的必要配套则提升到 P0。**

# 20. 普通 Aggregate / Transform 仍存在 BF16 intermediate → FP32 epilogue

## 20.1 Ordinary aggregate

部分非 High-D path：

```text
pulled BF16
×
W BF16
↓
at::matmul → BF16 aggregated
↓
BF16→FP32
× scale
+ bias
↓
FP32 out
```

High-D handwritten AMX 已经能：

```text
BF16 inputs
↓
AMX FP32 accumulator
↓
scale+bias
↓
FP32 out
```

直接避免 BF16 dense output。

因此普通 D<=128 也可以考虑复用类似 fused epilogue。

---

## 20.2 Transform-first

Transform-first：

```text
Hs BF16
× Wb
↓
T BF16
↓
sparse FP32 accumulate
↓
store BF16 aggregated
↓
final BF16→FP32 scale+bias
```

如果 aggregated 只为了立即变 FP32 output，可以让最终 sparse pull：

```text
FP32 accumulate
↓
直接 scale+bias
↓
FP32 out
```

避免：

```text
FP32 acc
→ BF16 store
→ BF16 load
→ FP32 out
```

---

## 20.3 判断

这些是**明确存在的 dtype boundary**，但 sparse graph traffic 常常仍是大头。

因此优先级低于：

```text
inter-layer traffic
terminal Gs/Q
D-slab repeated scan
static first-layer SX
```

**优先级：P2。**

# 21. Hidden-layer irregular source feature traffic 仍是最终系统大头之一

当前 CSR：

- 每一行内 neighbor id 已按升序；
- 但升序并不等于连续；
- source row 仍由图结构决定；
- 同一个 `H[src,:]` 可能服务很多 destination。

当前访问模式：

```text
dst0: H[100]
dst1: H[831]
dst2: H[100000]
...
dst50: H[100]
```

每次 edge 确实立即把一个 source feature row 用完；并不存在普通 K=128 path “先取一半、扫完整图、再取另一半”的情况。

真正的冗余来自：

> 同一 `H[src]` 在多个 destination 中再次被需要时，之前已经被 cache eviction，导致从 DRAM 重拉。

Authority 环境当前：

```bash
TFS_LOCALITY_SCHEDULE=off
TFS_HS_REPLICA=off
```

C++ 中有实验 locality scheduler，但它不是 final authority 默认路径。

---

## 21.1 这里不建议再做传统“共享邻居 destination 聚类”当主创新

可探索更不同的机制，例如：

### Per-worker L2-budgeted Hot-Source Microcache

只复制极少数高复用 source feature rows：

```text
[threads, N_hot, K]
```

而不是复制整个 `N×K`。

### 但必须先 profile

需要统计：

- source access histogram；
- top-X% source 覆盖多少 edge accesses；
- reuse distance；
- LLC load miss；
- DRAM BW；
- microcache hit potential。

如果热点不集中，就不值得做。

这个方向是**研究候选**，不是当前已确认的固定-shape bug。

# 23. 32T native 上限与 NUMA

```text

```

Native worker pool capacity也固定：

```text

```

```text

```

在 64 核/更多 NUMA domain 的 CPU 上无法直接扩到满核。

但这里不能简单认为：


- cross-NUMA reduction；
- graph/source placement；
- bandwidth saturation。

因此这更像**架构可扩展性问题**，而不是当前最优先的固定收益优化。

只要：

```text
sparse_scan_ms × slab_count
```

占明显比例，就进入 Phase C 的 native single-scan。

# 26. Phase B：当前 terminal 最大收益路线

## B1. Whole-Terminal Native Micro-Engine

一次 terminal 调用内：

```text
pack W / Wt once

for selected row macro panel:
    selected pull

    for micro panel:
        AMX logits
        exact CE
        Gs immediate
        dW accumulate
        Q produce

backward:
    compact rectangular pull
```

目标：

- 不保留 giant Gs panel；
- 不重复读取 Gs；
- Q native；
- W/Wt 一次 pack；
- microblock cache locality；
- db deterministic；
- tail logical stride。

---

## B2. Selected pull streaming

把：

```text
full P[M,K]
```

变成：

```text
P_panel
```

与 B1 同时接入。

---

## B3. Compact-active backward

给 Products 低 D / 高线程区域：

```text
compact grad
+
mature native active scheduling
```

但不创建 full `G[N,D]`。

# 31. 最终排序

如果现在只允许做 8 件事，建议顺序：

1. **Native Q = Gs W^T**
2. **Whole-Terminal Native Micro-Engine，消掉 giant Gs panel**
3. **Wide-K static first-layer `S X` cache**
4. **Inter-layer ReLU + Dropout + scale + FP32→BF16 fused bridge**
5. **True native single-scan D-slab backward**
6. **Compact-active backward，去 full `G[N,D]`**
7. **Selected pull streaming + compact selected-forward CSR/int32**
8. **修所有剩余 dtype/layout 往返与 versioned W packing**

其中：

- 1、2 是继续提高当前 IGB-2983 terminal 2.0965x 最直接的路线；
- 3 是静态 wide-K 首层可能出现“删除整次 sparse traversal”的结构性机会；
- 4 是解决 L3/L4 Amdahl 稀释的关键；
- 5 是 High-D arbitrary-D 真正从“内存安全”走向“高性能”的关键；
- 6 是 Products 低 D、高线程监督路径的重要缺口。

# 32. 最重要的判断

目前最大的风险不是“没有优化点”，而是**优化已经很多，但部分能力还没有贯通**。

权威 TFS 已经具备：

```text
AMX
AVX
panel
single scan
saved intermediate
BF16 pull
static cache
planner
```

新 supervision 路径又具备：

```text
selected sparse
rectangular backward
bounded CE
compact dW
compact logits
```

下一阶段真正有价值的工作不是继续发明新的孤立 kernel，而是：

\[
\boxed{
\text{让 dtype、layout、sparse scope、dense GEMM、loss 和 backward 在同一个数据流里只落地一次}
}
\]

从源码看，当前最明显仍未贯通的三条链正是：

```text
① hidden FP32 → activation → dropout → BF16 next layer

② terminal logits → CE → Gs → dW + Q

③ High-D D-slab → dP reduction → sparse A^T
```

这三条如果真正做成 single-pass / producer-consumer 风格，比继续调几个 tile 参数更有机会得到**显著的端到端收益**，也更容易形成统一的方法故事。
